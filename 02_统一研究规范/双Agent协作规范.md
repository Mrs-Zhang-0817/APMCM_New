# 双 Agent 协作规范 v1（2026-11-27）

适用对象：两名队员及分别协助他们的Q1 Agent、Q2 Agent。当前只建立规范，不启动专项计算或实验。统筹Agent负责汇总和共同文件整合，不代替两名队员决策。两条工作线是角色，不指定成员姓名或自动创建Agent会话。

## 1. 项目目标与启动阅读

Q1完成光谱异常检测、连续函数重构及十炉连续三维图；Q2完成累计供氧与CO2/CO异常调查、连续重构、供氧流率与累计排放计算及分流率运输延迟；Q3在统一目标和信息可用时间下融合两模态，用光谱实时预测烟气，评估跨炉泛化。共同交付数学合理、实验可验证、符合官方三问的论文方案。

每个Agent开始任务先读取00_项目管理/项目主文档.md、00_项目管理/当前项目进度.md、02_统一研究规范/统一数据质量标准.md、本文、00_项目管理/共同决策日志.md、03_共同数据分析/数据问题登记表.csv及本线最新报告。确认附件1修正版来源和01_赛题与原始数据/数据结构清单.json哈希；缺少来源/版本则登记阻塞，不回退旧版或编造。首次回复列出当前阶段、授权范围、将写入的路径、标准版本和待确认事项。

独占范围不等于自动授权正式清洗、拟合、训练。两个Agent可在当前阶段和共同标准内独立写调查代码、算统计、绘原值图、提出数学模型与候选实验设计、编写专项报告；后续方法比较实验须遵守阶段门槛。不能自行修改对方标准或成果，不能把建议算法写成最终方案。

## 3. 必须共同确认的九类事项

统一标准修改；原始数据重要解释与异常分类；跨炉统一策略；共同预处理；遮蔽及削顶/注入验证设计；Q3目标与信息可用时间；跨炉验证划分；论文核心数学方法；重大结论与假设。两个Agent只能提出建议和证据，不能代表队员签字。未确认事项登记Pending，阻塞依赖该事项的工作，其他独立调查可继续。

阶段门槛：整体审查收尾与标准确认→Q1/Q2专项调查→交换审核→队员共同选择预处理与验证设计→先实施验证并共同审核→正式预处理。随后再按官方要求推进重构与预测。当前不得以“实验”名义越过禁止插值、平滑、波长统一、正式拟合和训练的限制。

## 4. 单次任务与研究记录模板

每项重要任务使用以下字段，不可省略；不适用填原因，未知填未知。任务编号A-Q1-001或B-Q2-001，实验编号在任务后追加E01，跨线用J-编号。

|字段|填写要求|
|---|---|
|Task ID|唯一编号、作者/Agent角色、日期、文档版本|
|Research Question|可被证据回答的具体问题|
|Data Source|文件名、官方版本、SHA256、sheet、行列、炉号、变量、单位、时间/波长窗|
|Method|当前方法或设计，注明调查/候选实验/正式处理|
|Mathematical Principle|公式、符号与适用条件，不只写库函数名|
|Assumptions|假设、依据和可被推翻条件|
|Parameters|所有参数、来源、种子、环境及代码版本|
|Results|原始数量、分母、比例、逐炉结果；未执行则明确未执行|
|Evidence|输入清单、可复现入口、输出路径与哈希、局部图、审核依据|
|Limitations|缺失证据、可辨识性、适用工况、泄漏风险|
|Alternative Explanations|至少考虑合理替代解释；无则说明理由|
|Validation Method|检测/重构分别设计，是否实际执行、分炉隔离及评价定义|
|Conclusion|不超出证据的结论|
|Decision Status|下面六个结论状态之一；需共同决定时另记审批Pending|

结论状态互不混用：Observed Fact（观察事实）、Hypothesis（待验证假设）、Candidate Method（候选方法）、Experimentally Supported（实验支持）、Jointly Approved（双方共同确认）、Rejected（已否决）。状态属于具体主张，不是一整份报告的笼统标签；同一报告应逐条标注。实验支持不能自动升级双方确认。每次变更保留前状态、时间、证据和确认人。审批流程Pending/Approved/Rejected另列字段，Pending不冒充第七种结论状态。

问题记录使用本线ID A-Q1-DQ001、B-Q2-DQ001，并引用既有JQ编号，避免覆盖。将原值、候选标签、确认状态、清洗值、重构值分文件或明确分列保存，不能复用同一列抹去原值。掩码和比例遵守标准第15条。

## 5. 文件交接与唯一写入协议

1. 默认各Agent仅写独占范围；读取其他线成果，审核意见写自己的review文件，不直接改被审文件。
2. 共同文件只由当轮明确登记的整合人写。首次修改先在Joint_Decision_Log的维护栏登记整合人、作用范围、开始时间、基线版本及SHA256；未指定具体人时保持“待指定”，不允许两Agent各自猜测自己是整合人。
3. 提交者生成独立Proposal_<TaskID>_<角色>_vNN.md及变更说明，列当前共同文件哈希、建议diff、证据和影响；发送给队员/另一个Agent时由用户明确交接，不假定两个会话自动同步。
4. 整合前再核对文件哈希；若与提交基线不同，停止覆盖、重新比较合并，禁止以最后写入覆盖冲突。多机/多个项目副本也用同一规则，不按文件日期认定新旧。
5. 保留前版本到03_共同数据分析/分析证据/Protocol_Versions/<版本_任务ID>，不覆盖已有快照；审查通过后由唯一整合人一次发布版本和Changelog，记录修改前后哈希。写入期间其他Agent只读共同文件。若没有可靠协调条件，先只交proposal，不写共享文件。
6. 原始文件始终只读；所有处理产生新文件。脚本重复运行不得静默覆盖已发布结果：用Experiment_ID及版本命名，或输出到新run目录。实验记录包含命令、输入哈希、依赖、参数和输出清单。
7. 交接完成由接收方核对清单和哈希并记录收到的版本；解除写入占用。交接包为快照，本仓库中文正式位置是唯一当前源，快照不自动更新。外发时写明包版本和本次新增内容。

## 6. 交叉审核与冲突处理

Q1报告完成后由Q2 Agent审核，Q2由Q1 Agent审核。审核范围一致：来源可靠性和修正版、计算/分母与局部复算、数学假设及边界、反例和过度推断、标准18条遵守、时序泄漏与复现入口。审核者至少选择与主张直接相关的代表位置独立复算，记录选择理由；不得仅检查报告措辞或代码能运行。

作者提交冻结报告和输入/代码/结果清单→对方提交编号审核意见→作者逐条答复并出新版本→审核者记录解决/未解决→两名队员决定重大主张是否采纳。02_统一研究规范/交叉审核模板.md由整合人汇总，未给实际意见时保留模板，不编造审核通过。

冲突处理依次检查来源与版本、代码与参数、数学定义与假设，再复现实验、比较证据，最后由两名队员决定。不得覆盖对方结果或以简单投票代替证据。若证据不足，保留双方解释与Pending，注明依赖任务和需要补充的证据。
